# Belka

Бэкапы в облачные хранилища, восстановление из них и зеркалирование релизов GitHub. Есть консольная утилита `belka` для скриптов и планировщика (Windows, Linux, в том числе ARM64; один бинарник без зависимостей) и приложение для Windows и Android с файловым менеджером и автобэкапом.

---

## ✨ Возможности

**Провайдеры**

| Источник | Хранилище | Проверка «файл не изменился» |
|---|---|---|
| `yandex` | Яндекс.Диск (REST API) | размер + MD5 |
| `mailru` | Облако Mail.ru (WebDAV) | размер + дата изменения |
| `google` | Google Drive (API v3, resumable upload) | размер + MD5 |
| `webdav` | Nextcloud, ownCloud, Koofr, pCloud, 4shared, InfiniCLOUD, Synology и любой WebDAV | размер + дата (MD5 при `WEBDAV_ETAG_IS_MD5=true`) |
| `s3` | AWS S3, Cloudflare R2, Backblaze B2, Wasabi, Yandex Object Storage, Selectel, VK Cloud, Timeweb, Storj, DigitalOcean Spaces, MinIO | размер + MD5 (для multipart — дата) |
| `synology` | Synology NAS (File Station API) | размер + дата изменения |

Адреса и настройки популярных S3- и WebDAV-сервисов собраны в разделе [Пресеты S3 и WebDAV](#пресеты-s3-и-webdav). В приложении их можно выбрать из списка.

Облако в командах задаётся как `ИСТОЧНИК:ПУТЬ`, например `yandex:/Backups`. Источник — провайдер из таблицы, настроенный переменными окружения, аккаунт приложения на этом компьютере (`"Мой NAS:/Backups"`) или аккаунт из файла, экспортированного из приложения. Подробнее см. [Облака в командах](#облака-в-командах).

**`belka upload` — бэкап файла или папки.** Дерево каталогов воссоздаётся в облаке, неизменённые файлы пропускаются. Что уже загружено, Belka запоминает по размеру и дате, поэтому повторный запуск не перечитывает гигабайты неизменённых файлов. Если у провайдера нет MD5, сравнивается дата изменения: это важно для многотомных архивов, где все тома одного размера. Фильтры `--include` и `--exclude`, проверка после загрузки `--verify`, параллельные загрузки `-j`.

**Синхронизация** (`--delete-extra`). После успешной загрузки из облачной папки удаляется то, чего больше нет локально, как в `rclone sync`.

**Ротация бэкапов** (`--keep-last`, `--keep-days`). После успешной выгрузки старые бэкапы удаляются: остаются последние N штук или бэкапы за последние N дней. Бэкап распознаётся по дате в имени, тома многотомного архива удаляются вместе. Затрагиваются только серии бэкапов, которые записал этот запуск. Подробнее см. [Ротация](#ротация-старых-бэкапов).

**`belka restore` — восстановление.** Папка или файл из облака скачиваются на диск. Неизменённые файлы пропускаются, прерванное восстановление продолжается с места остановки. Подробнее см. [Восстановление](#восстановление-из-облака).

**`belka mirror` — зеркалирование ссылок** из `urls.txt`:
* `https://github.com/owner/repo` — последний релиз; `.../releases/tag/<tag>` — конкретный релиз. Ассеты, подходящие под `--assets`, сохраняются в `ПУТЬ/{repo}/[tag] имя_файла`. Старые версии того же файла удаляются **только после** успешной загрузки новой. Чужие файлы не трогаются.
* Любые прямые ссылки. Размер и дата файла на сервере проверяются запросом HEAD, поэтому неизменённый файл не скачивается заново.

**Автобэкап в приложении.** Папки компьютера или телефона, например фото с камеры, регулярно копируются в облако: только новые и изменённые файлы. На Android — по Wi‑Fi и даже при закрытом приложении, с освобождением места на телефоне. Подробнее см. [Автобэкап](#автобэкап).

**Уведомления.** Итог запуска уходит в Telegram, webhook (Slack, Discord, Mattermost) и сервис мониторинга вроде healthchecks.io: если бэкап сломался или перестал запускаться, вы узнаете об этом сразу. Подробнее см. [Уведомления](#уведомления).

**Шифрование** (любой провайдер, формат [rclone crypt](https://rclone.org/crypt/)). Файлы шифруются на вашем компьютере до отправки и расшифровываются после скачивания, облако видит только шифротекст. Имена файлов и папок тоже можно шифровать. Зашифрованное Belka открывается в rclone, и наоборот. Подробнее см. [Шифрование](#шифрование).

**Надёжность**
* Повторы с экспоненциальной задержкой при сетевых сбоях, 5xx и 429 (с учётом `Retry-After`), в том числе для самих загрузок.
* Без общего тайм-аута на передачу: многогигабайтные файлы не обрываются. Зависшие соединения отсекаются keep-alive и тайм-аутом, пропорциональным размеру.
* Ограниченное потребление памяти: файлы передаются потоком. S3 загружает файлы больше 64 МБ частями (multipart), Google Drive продолжает прерванную загрузку с места обрыва.
* Скачивание пишет во временный `.belka.part` и докачивает с места обрыва через `Range`. Существующий файл заменяется только полностью скачанным.
* Дата изменения файла сохраняется в облаке там, где провайдер это умеет: Google Drive, Nextcloud и ownCloud, S3 (метаданные `mtime`, как у rclone), Synology.
* Ничего не удаляется, если загрузка прошла с ошибками. Удаление в корне `/` запрещено.
* `--dry-run` показывает, что будет загружено или удалено, ничего не меняя.
* Коды возврата для скриптов: `0` успех, `1` фатальная ошибка, `2` неверные аргументы, `3` часть файлов не удалась, `130` прервано Ctrl+C.

## 🗂 Структура

Репозиторий — Cargo workspace:

| Каталог | Что внутри |
|---|---|
| `crates/core` | Провайдеры облаков, HTTP-ретраи, движок синхронизации (`sync`): сканирование с фильтрами, индекс, загрузка, скачивание, удаление лишнего |
| `crates/store` | Аккаунты и пароли (связка ключей ОС или файл), экспорт `.belka`, задачи автобэкапа. Общий для приложения и CLI |
| `crates/cli` | Консольная утилита `belka` для скриптов и планировщика |
| `gui/` | Приложение на Tauri 2 + Svelte: для Windows и для Android (`gui/src-tauri/gen/android`) |

## 🚀 Сборка

Требуется Rust 1.89+. Команды `cargo` без `-p` собирают только CLI.

```cmd
build.bat          # всё: CLI для Windows, GUI и CLI для Linux x86_64 и ARM64
build.bat exe      # только CLI для Windows
build.bat gui      # только GUI: dist\belka-gui.exe и установщик
build.bat linux    # только Linux x86_64 (через zig)
build.bat arm64    # только Linux ARM64 (через zig)
build.bat android  # только Android: dist\belka-<версия>-arm64.apk
```
Готовые файлы складываются в `dist/`.

Версия задаётся в `Cargo.toml` и `gui/package.json`. Чтобы поменять её в обоих файлах сразу, есть `version.bat X.Y.Z` (без аргумента скрипт покажет текущую).

Ручная сборка:
```bash
cargo build --release                                          # текущая платформа
cargo build --release --target x86_64-unknown-linux-musl       # Linux x86_64
cargo zigbuild --release --target aarch64-unknown-linux-musl   # Linux ARM64
cargo test --workspace                                         # тесты
```

GUI (нужен Node.js 20+):
```bash
cd gui
npm install
npm run tauri dev      # запуск в режиме разработки
npm run tauri build    # установщик в target/release/bundle/
```
Аккаунты приложения хранятся в `accounts.json` в папке настроек приложения, а пароли и токены — в системном хранилище учётных данных (Windows Credential Manager, Keychain, Secret Service). Консольная `belka` на том же компьютере видит эти аккаунты, см. [Облака в командах](#облака-в-командах).

#### Вход через браузер (Google Drive, Яндекс.Диск)

Обычно достаточно нажать «Войти через браузер»: используется OAuth-приложение, встроенное в сборку. Своё приложение нужно, если в сборке его нет или вы хотите собственную квоту API. Для этого в диалоге «Новый аккаунт» отметьте «Своё OAuth-приложение». Введённые данные запоминаются.

* **Google**: в Google Cloud Console включите Google Drive API, настройте OAuth consent screen (в режиме Testing добавьте свой адрес в тестовые пользователи) и создайте OAuth client ID типа **Desktop app**. Нужны Client ID и Client secret: для настольных приложений secret не считается секретом.
* **Яндекс**: на [oauth.yandex.ru](https://oauth.yandex.ru/) создайте приложение с платформой «Веб-сервисы», Redirect URI `http://127.0.0.1:53682/` и доступами Яндекс.Диска: чтение, запись, информация о Диске. Достаточно Client ID: вход идёт по PKCE.

Встроенное приложение задаётся при сборке GUI и CLI:
```cmd
set BELKA_GOOGLE_CLIENT_ID=...apps.googleusercontent.com
set BELKA_GOOGLE_CLIENT_SECRET=...
set BELKA_YANDEX_CLIENT_ID=...
npm run tauri build
```
Токен Яндекса действует год, после этого нужно войти заново.

#### Предпросмотр

Пробел, двойной щелчок или «Просмотр» в контекстном меню показывают файл из облака без сохранения: картинки, видео, аудио, PDF и текст (UTF-8 и Windows-1251, первый мегабайт). Стрелки ← → листают файлы папки. Файл скачивается во временный кэш приложения, который очищается при запуске; файлы больше 100 МБ скачиваются только после подтверждения. В зашифрованных папках файлы расшифровываются на лету.

#### Ссылки на файлы

В контекстном меню облака есть «Поделиться ссылкой» и «Закрыть доступ по ссылке» (Яндекс.Диск, Google Drive, Облако Mail.ru). Объект становится доступен на чтение всем, у кого есть ссылка, а сама ссылка копируется в буфер обмена. В Google закрывается только доступ по ссылке: доступ, выданный конкретным людям, остаётся.

Для ссылок в Mail.ru нужен пароль приложения с полным доступом, подробнее см. [Облако Mail.ru](#облако-mailru).

#### Автобэкап

Задача копирует локальную папку, например `DCIM` на телефоне или «Документы» на компьютере, в папку облака по расписанию: раз в час, раз в сутки, раз в неделю и т.п. Задач может быть сколько угодно. На компьютере — кнопка с часами рядом с выбором аккаунта, на телефоне — меню → «Автобэкап» или «Автобэкап этой папки» у выделенной папки.
* Загружаются только новые и изменённые файлы, подпапки воссоздаются. В облаке ничего не удаляется и не ротируется, даже если файл удалён локально.
* Уже загруженные файлы запоминаются по размеру и дате, поэтому повторный запуск не читает их и не обращается к облаку. При первом запуске файлы сверяются с облаком (размер и MD5 или дата), так что уже лежащее там, например после Synology Drive, повторно не загружается. Если у задачи сменить папку или облако, она начинает с нуля.
* Скрытые файлы и папки пропускаются, в том числе миниатюры и корзина галереи (`.trashed-…`). Можно задать маски: «только эти файлы» (`*.jpg, *.mp4`) и «пропускать» (`*.tmp, cache`), синтаксис как у [фильтров CLI](#фильтры).
* На экране задачи видна история последних 20 запусков; у запуска с ошибками по нажатию раскрывается список файлов, которые не загрузились, с причинами.
* Ошибки показываются по-русски: известные сообщения переводятся, а для сетевых и HTTP-ошибок к пояснению добавляются подробности.

**На телефоне.** Расписание ведёт Android (WorkManager): бэкап запускается, даже если приложение закрыто, и ждёт условий «только по Wi‑Fi» и «только на зарядке». Время запуска приблизительное, система может сдвинуть его ради экономии батареи. Кнопка ▶ запускает задачу сразу при любой сети. Прогресс виден в уведомлении и на экране «Автобэкап». Если загрузка прервалась, например пропал Wi‑Fi, следующий запуск продолжит с того места.

**Освобождать место на телефоне** (по желанию): файлы старше выбранного срока (неделя, месяц, 3 месяца, год) удаляются с телефона, если они уже есть в облаке. Перед удалением облако спрашивается заново и сверяется размер: одной памяти о прошлой загрузке для удаления недостаточно. Галерея узнаёт об удалении сразу.

**На компьютере.** Задачи выполняются, пока приложение открыто: раз в минуту оно проверяет, у каких подошло время. Запуск, закончившийся ошибками (например, не было сети), повторяется через час, не дожидаясь полного интервала. Одна задача никогда не выполняется дважды одновременно, даже если её запустили и приложение, и `belka task run`. Чтобы бэкап шёл и при закрытом приложении, добавьте в Планировщик заданий `belka task run --due` с повтором раз в час, см. [Задачи автобэкапа из CLI](#задачи-автобэкапа-из-cli).

#### Android

Та же программа в виде одной панели: вверху переключатель «Облако / Телефон». Долгое нажатие выделяет файлы. «Скачать» и «Загрузить в облако» переключают на другую сторону, там нужно открыть папку назначения и нажать «Скачать сюда» или «Загрузить сюда». Передачи продолжаются в фоне, прогресс виден в уведомлении. Системная кнопка «Назад» закрывает меню, снимает выделение и поднимается на уровень вверх.

* При первом открытии телефона приложение попросит «Доступ ко всем файлам»: с ним видны все папки, включая карты памяти.
* Аккаунты удобно перенести с компьютера: «Аккаунты → Экспорт…» в Windows, затем «Импорт…» на телефоне.
* Пароли и токены хранятся в закрытой папке приложения, доступной только ему.
* Раз в сутки приложение проверяет релизы на GitHub и предлагает скачать новую версию APK.

Сборка требует Android Studio (JDK, SDK) и NDK из её SDK Manager, а также Rust-цель `aarch64-linux-android`. `build.bat android` находит их сам. APK подписывается ключом из `gui/src-tauri/gen/android/keystore.properties`:
```properties
storeFile=C:/Users/me/.belka/belka-release.jks
storePassword=...
keyAlias=belka
keyPassword=...
```
Этот файл и сам ключ в git не попадают. Храните копию ключа: обновить приложение, подписанное другим ключом, можно только после удаления старой версии.
Релиз собирает GitHub Actions (`.github/workflows/android.yml`) по тегу `v*` и прикладывает APK к релизу. Нужны секреты репозитория `ANDROID_KEYSTORE_BASE64` (ключ в base64), `ANDROID_KEYSTORE_PASSWORD` и `ANDROID_KEY_ALIAS`, а для встроенного входа через браузер ещё и `BELKA_*`.

## ⚙️ Настройка

Аккаунты приложения на этом компьютере и файл экспорта `.belka` не требуют настройки, см. [Облака в командах](#облака-в-командах). Ниже — настройка источников-провайдеров через переменные окружения.

Скопируйте [.env.example](.env.example) в `.env` в текущую папку или рядом с программой либо укажите `--env-file`. Системные переменные окружения имеют приоритет над `.env`. `CLOUD_JOBS` из `.env` работает как значение по умолчанию для `-j`.

`belka providers` выводит переменные, нужные каждому провайдеру. Проверить настройку проще всего командой `belka ls yandex:/`.

**Google Drive и Яндекс.Диск.** Токен проще всего получить командой `belka login google` (или `yandex`): откроется браузер, а после входа программа выведет строки для `.env`. Сообщения идут в stderr, поэтому можно сразу дописать файл: `belka login google >> .env`. Вход нужен на компьютере с браузером, полученные строки можно перенести на сервер.

Для Google выводится `GOOGLE_REFRESH_TOKEN`, по нему access token обновляется автоматически. Refresh token работает только с тем OAuth-приложением, для которого выдан. Со встроенным приложением хватает одного токена. Если заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, вход и работа идут через ваше приложение (тип Desktop, scope `https://www.googleapis.com/auth/drive`). Вместо refresh token можно указать `GOOGLE_DRIVE_TOKEN`, но access token живёт около часа.

#### Облако Mail.ru

Обычный пароль от почты не подойдёт: нужен пароль для внешних приложений («Пароль и безопасность → Пароли для внешних приложений»). При создании выбирается уровень доступа:

| Уровень доступа | Файлы (WebDAV) | Ссылки в GUI |
|---|---|---|
| Полный доступ к Облаку (WebDAV) | ✅ | ❌ «username or password is incorrect» |
| Полный доступ к Почте, Облаку и Календарю (все протоколы) | ✅ | ✅ |

Ссылки создаются через API самого облака, а не через WebDAV, и с паролем только для WebDAV Mail.ru в этот API не пускает. Пароль в уже добавленном аккаунте поменять нельзя: удалите аккаунт и добавьте его заново.

**S3.** Используются path-style запросы (`{endpoint}/{bucket}/{key}`). В S3 нет настоящих папок, поэтому пустые каталоги не создаются. Регион подписи (`S3_REGION`) для известных сервисов определяется по адресу endpoint, для остальных по умолчанию берётся `us-east-1`. Если сервер отвечает ошибкой подписи, укажите регион явно.

#### Пресеты S3 и WebDAV

Многие хранилища работают по протоколу S3 или WebDAV, поэтому подключаются через провайдеры `s3` и `webdav`, отдельный код для них не нужен. В GUI при добавлении аккаунта S3 или WebDAV есть список «Сервис»: выбранный сервис подставляет известный адрес (или пример адреса, если он у каждого свой) и показывает, где взять ключи. В CLI те же значения указываются в `.env`.

**S3** (источник `s3:`). Регион в колонке «Регион» определяется автоматически, задавать `S3_REGION` не нужно.

| Сервис | `S3_ENDPOINT` | Регион | Где взять ключи |
|---|---|---|---|
| Amazon S3 | `https://s3.<регион>.amazonaws.com` | из адреса | IAM → Users → Security credentials |
| Cloudflare R2 | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` | `auto` | R2 → Manage API tokens |
| Backblaze B2 | `https://s3.<регион>.backblazeb2.com` (указан на странице бакета) | из адреса | Application Keys: keyID и applicationKey |

Адрес в ссылке DSM берёт из своих настроек (Панель управления → Внешний доступ).

#### Шифрование

Формат полностью совпадает с rclone crypt: содержимое шифруется XSalsa20-Poly1305 блоками по 64 КБ, имена — AES-256 в режиме EME, ключи получаются из пароля через scrypt. Belka и rclone читают файлы друг друга.

**Пароль не восстанавливается.** Без него файлы не расшифровать ни Belka, ни rclone, ни кому-либо ещё.

**В GUI.** «Новый аккаунт → Зашифрованная папка»: выберите подключённое облако, папку в нём (например `/Encrypted`) и пароль. Папка появится отдельным аккаунтом: всё, что загружается в неё, шифруется, а при просмотре и скачивании расшифровывается. Пароль хранится в системном хранилище учётных данных. Если в папке уже есть файлы, Belka проверит, что они расшифровываются этим паролем. Облако, в котором лежат зашифрованные папки, нельзя удалить, пока не удалены они. В обычном облаке зашифрованная папка и её содержимое помечены замком, а двойной щелчок по такой папке открывает её расшифрованный вид.

**В CLI** зашифрованная папка приложения доступна как источник по своему названию (`"Шифр:/Backups"`). Для источника-провайдера шифрование включается переменной `CRYPT_PASSWORD`:

| Переменная | Что задаёт |
|---|---|
| `CRYPT_PASSWORD` | пароль; если задан, все файлы шифруются |
| `CRYPT_PASSWORD2` | необязательная соль, `password2` в rclone |
| `CRYPT_ROOT` | папка облака с зашифрованным деревом, по умолчанию `/` |
| `CRYPT_FILENAMES` | `standard` (по умолчанию, имена шифруются) или `off` |

Путь отсчитывается внутри `CRYPT_ROOT`: с `CRYPT_ROOT=/Encrypted` и `yandex:/Backups` файлы лягут в `/Encrypted/<шифрованное «Backups»>/…`. Чтобы видеть эти бэкапы в GUI, создайте зашифрованную папку `/Encrypted` с тем же паролем.

**Как открыть в rclone:** remote типа `crypt` с `remote = <облако>:<папка>`, тем же паролем и `filename_encryption = standard` (или `off`). В `rclone.conf` пароли хранятся в скрытом виде, а Belka нужен исходный пароль: его показывает `rclone reveal`.

Шифрование идёт на лету, без временных файлов: данные шифруются блоками по 64 КБ во время отправки и расшифровываются во время скачивания. Возобновление прерванной загрузки (Google Drive) и докачка работают и для зашифрованных файлов.

Ограничения:
* MD5 у зашифрованных файлов не совпадает с исходным, поэтому неизменённые файлы определяются по размеру и дате. При зеркалировании прямая ссылка без тега версии загружается заново, если сервер не сообщает размер и дату файла.
* Зашифрованное имя длиннее исходного. У облаков с лимитом 255 символов на имя исходное имя должно быть не длиннее примерно 140 байт (около 70 кириллических символов).
* Ссылками на зашифрованные файлы делиться нельзя: получатель увидит только шифротекст.

### Облака в командах

Облачная папка записывается как `ИСТОЧНИК:ПУТЬ`. Путь отсчитывается от корня облака, пустой путь означает корень (`yandex:`). Источник ищется так:
1. Если задан `--accounts FILE`, сначала среди аккаунтов этого файла.
2. Имя провайдера: `yandex`, `mailru`, `google` (`gdrive`), `webdav` (`nextcloud`), `s3` (`r2`, `minio`), `synology` (`nas`). Настройки берутся из переменных окружения и `.env`, см. [Настройка](#️-настройка).
3. Аккаунт приложения Belka на этом компьютере, по названию без учёта регистра: `"Яндекс личный:/Backups"`. Пароли и токены читаются из системного хранилища учётных данных, поэтому на Windows и macOS настройка не нужна. `belka accounts` покажет названия.

На сервере без приложения удобно использовать экспорт: в приложении «Аккаунты → Экспорт…», файл `.belka` перенести на сервер и указать его в `--accounts` (или `BELKA_ACCOUNTS`), а пароль от него — в `BELKA_ACCOUNTS_PASSWORD`. Файл содержит все пароли и токены, поэтому пароль экспорта должен быть не короче 8 символов; лучше длиннее. Так на сервер попадают и зашифрованные папки, и токены, полученные входом через браузер.

### Фильтры

`--include` и `--exclude` принимают маски: `*` — любые символы, кроме `/`; `**` — любые символы, в том числе `/`; `?` — один символ. Регистр не учитывается. Маска без `/` проверяется по каждому имени в пути, маска с `/` — по пути от корня копируемой папки.

```powershell
belka upload D:\Photos yandex:/Photos --include "*.jpg" --include "*.mp4"
belka upload D:\Project "NAS:/Project" --exclude node_modules --exclude "*.tmp" --exclude "/build/**"
```
Исключённые файлы не удаляются из облака и при `--delete-extra`: они не участвуют в копировании.

### Что уже загружено

Для каждой пары «локальная папка → облачная папка» Belka хранит индекс: какие файлы загружены и с какими размером и датой. Файл с теми же размером и датой больше не читается и не сверяется с облаком. Это главное, что ускоряет повторные бэкапы больших папок. Индексы лежат в `%LOCALAPPDATA%\belka\index` (Linux: `~/.cache/belka/index`). Если файл в облаке удалили или повредили вручную, запустите с `--no-index`: каждый файл будет сверен с облаком заново.

### Дата в пути

В пути можно подставить текущую локальную дату и время:

| Шаблон | Пример |
|---|---|
| `{date}` | `2026-10-15` |
| `{time}` | `03-00-00` |
| `{datetime}` | `2026-10-15_03-00-00` |

`belka upload D:\Data "yandex:/Backups/{date}"` каждый день кладёт копию в новую папку: `/Backups/2026-10-15`, `/Backups/2026-10-16` и так далее. Учтите, что в новую папку каждый раз загружается всё целиком. Другие шаблоны в фигурных скобках считаются ошибкой.

### Примеры

```powershell
# Папка бэкапа на Яндекс.Диск
belka upload D:\Backups\Daily yandex:/Backups/Daily

# Сначала посмотреть, что изменится, затем синхронизировать с удалением лишнего
belka upload D:\Site mailru:/Site --delete-extra -n
belka upload D:\Site mailru:/Site --delete-extra

# Cloudflare R2, 6 параллельных загрузок, со сверкой после загрузки
belka upload C:\Data s3:/daily-snapshots -j 6 --verify

# Аккаунт приложения по названию
belka upload D:\Photos "Мой NAS:/home/Photos" --include "*.jpg"

# Ежедневная копия в папку с датой, хранить 14 последних
belka upload D:\Data "yandex:/Backups/{date}" --keep-last 14

# Восстановить копию за 15 октября
belka restore yandex:/Backups/2026-10-15 D:\Restore

# Зеркалирование релизов, только .apk
belka mirror google:/Mirror --assets "(?i)\.apk$"

# Что лежит в облаке
belka ls webdav:/Backups -R
```

### Ротация старых бэкапов

Ротация удаляет из облака старые бэкапы, чтобы они не копились бесконечно. Она включается ключами `--keep-last N` и/или `--keep-days N` команды `upload` и работает сразу после выгрузки.

**Как Belka находит бэкапы.** Бэкапом считается файл или папка, в имени которых есть дата. Поддерживаемые форматы:

| Пример имени | Распознанная дата |
|---|---|
| `db_2026-10-15.sql.gz` | 15.10.2026 |
| `2026_10_15`, `2026.10.15`, `20261015` | 15.10.2026 |
| `site-20261015_0300.7z` | 15.10.2026 03:00 |
| `site 2026-10-15 03-00-15.zip`, `x_2026-10-15T030015.tar` | 15.10.2026 03:00:15 |

Год должен быть от 1990 до 2200, а дата существующей. Файлы и папки **без даты в имени ротация никогда не трогает**: `urls.txt`, `readme.txt`, `backup.zip` останутся на месте.

**Серии.** Имена, которые отличаются только датой, образуют серию: `db_2026-10-14.sql.gz` и `db_2026-10-15.sql.gz` относятся к серии `db_*.sql.gz`, а `site_2026-10-15.7z` — к серии `site_*.7z`. Правила применяются к каждой серии отдельно. **Ротируются только серии, в которые записал текущий запуск**: если загружен `db_2026-10-16.sql.gz`, ротация затронет только `db_*.sql.gz`, а отчёты `report_2025-01-01.pdf` или фото `IMG_20250101_…jpg` в той же папке останутся нетронутыми.

**Многотомные архивы.** Тома одного архива (`.7z.001`, `.7z.002`, …, `.part01.rar`, `.z01`, `.r00`) считаются одним бэкапом и удаляются вместе.

**Правила.**
* `--keep-last N`: в серии остаются N самых новых бэкапов (по дате из имени).
* `--keep-days N`: остаются бэкапы, датированные последними N днями, включая сегодня. `--keep-days 7` от 15 октября сохранит бэкапы с 9 по 15 октября.
* Если заданы оба ключа, бэкап остаётся, когда его сохраняет **хотя бы одно** правило. `--keep-last 3 --keep-days 30` хранит всё за месяц, но не меньше трёх бэкапов, даже если бэкапы давно не делались.

**В какой папке.** Обычно ротация работает в целевой папке. Если в пути есть шаблон даты, ротация идёт в родительской папке первого сегмента с шаблоном: для `"yandex:/Backups/{date}"` это `/Backups`, и бэкапами там будут папки `2026-10-14`, `2026-10-15`, … Учитываются только элементы, лежащие прямо в этой папке.

**Защита от потери данных.**
* Если при выгрузке хоть один файл не загрузился, ни ротация, ни `--delete-extra` не выполняются: неудачная новая копия не должна стоить удачной старой.
* Не удаляется то, что записал текущий запуск: загруженный файл, папка с датой из шаблона, а при выгрузке папки — всё, что лежит в ней на верхнем уровне.
* С `--dry-run` ротация только показывает, что удалила бы.
* Если удаление не удалось, код возврата будет `3`.

**Типичные схемы.**

Архив с датой в имени: скрипт создаёт архив, Belka выгружает его и удаляет лишние.
```powershell
$name = "db_$(Get-Date -Format yyyy-MM-dd).7z"
7z a "D:\Out\$name" D:\Database
belka upload "D:\Out\$name" s3:/Backups --keep-last 7
```
```bash
name="db_$(date +%F).tar.gz"
tar czf "/tmp/$name" /var/lib/app && ./belka -q upload "/tmp/$name" yandex:/Backups --keep-days 30
```

Копия папки целиком, по папке на каждый день:
```powershell
belka upload D:\Data "yandex:/Backups/{date}" --keep-last 7
```

### Восстановление из облака

`belka restore` работает в обратную сторону: содержимое облачной папки скачивается в локальную.

```powershell
# Вся папка: /Backups/2026-10-15/… → D:\Restore\…
belka restore yandex:/Backups/2026-10-15 D:\Restore

# Один файл: сохранится как D:\Restore\db_2026-10-15.7z
belka restore s3:/Backups/db_2026-10-15.7z D:\Restore

# Посмотреть, что будет скачано
belka restore yandex:/Backups/2026-10-15 D:\Restore -n
```

Как это работает:
* Локальный путь — всегда папка; если её нет, она создаётся. Содержимое облачной папки со всеми подпапками попадает прямо в неё, а файл сохраняется в ней под своим именем.
* Уже существующие файлы с тем же размером и тем же MD5 (если облако его отдаёт) или той же датой изменения пропускаются. Поэтому прерванное восстановление можно просто запустить заново. `-f` скачивает всё заново.
* Каждый файл пишется во временный `.belka.part` и докачивается после обрыва связи. Существующий файл заменяется только полностью скачанным.
* Скачанным файлам ставится дата изменения из облака. Так последующая выгрузка этих же файлов обратно увидит их неизменёнными.
* Файлы, которых нет в облаке, в локальной папке не удаляются.
* Имена, недопустимые в Windows (`:`, `*`, `?` и т. п.), а также `..` заменяются безопасными (`_`), и в лог пишется предупреждение.
* **Шифрование.** Файлы зашифрованной папки приложения или источника с `CRYPT_PASSWORD` расшифровываются при скачивании; путь указывается в незашифрованном виде.

### Ссылки из командной строки

`belka share` делится файлом или папкой по ссылке, печатает ссылку и копирует её в буфер обмена. Цель — облачный путь `ИСТОЧНИК:ПУТЬ` или файл в сетевой папке Synology: `\\NAS\docs\…` или подключённый диск.

```powershell
belka share "Яндекс личный:/Отчёты/2026-10.pdf"
belka share Z:\disk\Иванов.7z --expires 7      # Z: = \\192.168.1.10\public → /public/disk/Иванов.7z
belka share Z:\disk\a.7z Z:\disk\b.7z          # в буфер «a.7z: ссылка» и «b.7z: ссылка» построчно
belka share Z:\disk\Иванов.7z --unshare
```

* Сетевая папка (шара) Synology — это папка верхнего уровня в File Station. NAS ищется среди аккаунтов Synology по адресу. `\\NAS` и `192.168.1.10` считаются одним и тем же NAS, если имя разрешается в этот адрес. Если NAS не находится, укажите аккаунт через `--account`.
* Без `--expires` и `--password` повторный вызов возвращает уже созданную ссылку, а с ними прежняя ссылка заменяется новой.
* Срок действия и пароль ссылки поддерживает только Synology.

Загрузить и сразу поделиться можно одной командой: `upload --share`. Если загружен файл, ссылка ведёт на него, если папка — на облачную папку, куда она загружена. Ссылка создаётся, только если всё загрузилось без ошибок. Если облако не умеет такие ссылки (например, `--expires` на Яндекс.Диске или зашифрованная папка), команда завершается до загрузки.

```powershell
belka upload Z:\disk\Иванов.7z "Яндекс:/Клиенты" --share
belka upload D:\Отчёт "Synology NAS:/public/Клиенты/Иванов" --share --expires 14
```

Total Commander: кнопка на панели инструментов с командой `belka.exe` и параметрами `share %S --expires 7` делится выделенными файлами.

### Задачи автобэкапа из CLI

Задачи, созданные в приложении на компьютере, можно запускать и без него — например, из Планировщика заданий Windows:
```powershell
belka task list                 # задачи и итоги последних запусков
belka task run "Документы"      # одна задача сейчас
belka task run --due            # задачи, у которых подошло время
```
Добавьте в Планировщик `belka task run --due` с повтором каждый час: задачи будут выполняться по своему расписанию, даже когда приложение закрыто. История запусков общая с приложением. Задачи хранятся в папке настроек приложения (`%APPDATA%\io.github.tatarinovs.belka`, её можно переопределить переменной `BELKA_CONFIG_DIR`).

### Уведомления

Belka сообщает об итоге запуска в один или несколько каналов. Каналы включаются переменными в `.env` или окружении:

| Канал | Переменные | Что приходит |
|---|---|---|
| Telegram | `NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT` | текстовое сообщение |
| Webhook | `NOTIFY_WEBHOOK_URL` | POST с JSON |
| Пинг мониторинга | `NOTIFY_PING_URL` | запросы в стиле [healthchecks.io](https://healthchecks.io) |

Дополнительно:
* `NOTIFY_ON` (или `--notify-on`): `failure` (по умолчанию) пишет в Telegram и webhook только о проблемах, `always` — о каждом запуске.
* `NOTIFY_NAME`: название задания в сообщениях, например `nightly-db`. Полезно, если заданий несколько.
* `NOTIFY_TELEGRAM_API`: адрес Bot API, по умолчанию `https://api.telegram.org`. Пригодится, если доступ к Telegram заблокирован: можно указать свой [сервер Bot API](https://github.com/tdlib/telegram-bot-api) или обратный прокси.

Уведомления отправляют `upload`, `restore`, `mirror` и `task run` (по сообщению на каждую задачу).

**Статусы.** Сообщение отправляется в конце каждого запуска с одним из статусов:

| Статус | Когда | Код возврата |
|---|---|---|
| ✅ `success` | всё загружено (или скачано) | `0` |
| ⚠️ `partial` | часть файлов или удалений не удалась | `3` |
| ❌ `failure` | фатальная ошибка: нет доступа, неверные настройки | `1` |
| ⏹ `interrupted` | прервано Ctrl+C | `130` |

Пример сообщения:
```text
⚠️ Backup finished with errors — nightly-db
Host: SERVER01
Target: yandex:/Backups/2026-10-15
Files: 12 uploaded (1.2 GB), 30 unchanged, 1 failed
Deleted: 2
Time: 5m 12s
```

**Проверка.** `belka notify-test` отправляет тестовое сообщение во все настроенные каналы и сообщает, какой сработал, а какой нет.

Важно знать:
* При `--dry-run` уведомления не отправляются, чтобы пробный запуск не выглядел для мониторинга как настоящий бэкап.
* Ошибка отправки уведомления пишется в лог как предупреждение и не меняет код возврата.
* Об ошибках в аргументах и настройках, найденных до начала работы (неизвестный источник, нет переменных провайдера), уведомлений нет.
* Токен бота не попадает в лог даже при ошибках сети.

#### Telegram

1. Напишите [@BotFather](https://t.me/BotFather) команду `/newbot` и получите токен вида `123456789:AAH…`. Это `NOTIFY_TELEGRAM_TOKEN`.
2. Узнайте ID чата (`NOTIFY_TELEGRAM_CHAT`):
   * **личные сообщения:** напишите боту что угодно и откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, ID — поле `chat.id`;
   * **группа:** добавьте бота в группу, напишите в ней сообщение и посмотрите `getUpdates`, ID группы отрицательный;
   * **канал:** добавьте бота администратором канала с правом публикации; ID канала имеет вид `-100…`, можно указать и `@имя_канала` для публичного канала.
3. Проверьте: `belka notify-test`.

#### Webhook

На `NOTIFY_WEBHOOK_URL` отправляется POST с JSON:
```json
{
  "status": "partial",
  "name": "nightly-db",
  "host": "SERVER01",
  "mode": "upload",
  "target": "yandex:/Backups/2026-10-15",
  "processed": 43, "transferred": 12, "unchanged": 30, "deleted": 2, "failed": 1,
  "bytes": 1288490188,
  "duration_secs": 312,
  "error": null,
  "version": "1.1.0",
  "text": "⚠️ Backup finished with errors — nightly-db\n…",
  "content": "⚠️ Backup finished with errors — nightly-db\n…"
}
```
`mode` принимает значения `upload`, `restore`, `mirror` или `task`, `transferred` и `bytes` — загруженное (при восстановлении — скачанное), `error` — текст фатальной ошибки. Готовый текст сообщения лежит сразу в двух полях: `text` читают входящие webhook Slack, Mattermost и Rocket.Chat, а `content` — Discord. Поэтому адрес их webhook можно указать как есть. Для своих систем (n8n, Home Assistant, скрипт) используйте остальные поля.

#### Мониторинг (healthchecks.io)

Уведомление приходит, когда запуск закончился ошибкой. Но если бэкап перестал запускаться совсем (выключен сервер, сломан планировщик), сообщать будет некому. Эту проблему решает «dead man's switch»: сервис мониторинга ждёт сигнал по расписанию и бьёт тревогу, если сигнал не пришёл.

1. Создайте check на [healthchecks.io](https://healthchecks.io) (или на своём сервере Healthchecks), задайте период и допустимую задержку под ваше расписание.
2. Укажите его адрес: `NOTIFY_PING_URL=https://hc-ping.com/<uuid>`.

Belka отправляет POST на `<URL>/start` в начале запуска (сервис измеряет длительность и замечает зависшие запуски), на `<URL>` при успехе и на `<URL>/fail` при любой проблеме. В теле запроса — текст отчёта, он виден в журнале событий check'а. Пинг отправляется после каждого запуска, независимо от `NOTIFY_ON`.

### Запуск по расписанию (cron)

```bash
0 3 * * * cd /opt/belka && ./belka -q upload /srv/backups yandex:/Backups >> /var/log/belka.log 2>&1 || echo "backup failed: $?"
```
Ненулевой код возврата означает проблему: `3` — часть файлов не загрузилась (подробности в логе). Чтобы узнавать о проблемах без чтения логов, настройте [уведомления](#уведомления). Защитите `.env` и файл `.belka` правами `chmod 600`. Пароли и токены берутся из `.env` и переменных окружения, а не из аргументов, поэтому не видны в списке процессов. Единственный ключ с секретом, `--password` для ссылок, можно заменить переменной `BELKA_SHARE_PASSWORD`.

> **Git Bash на Windows** превращает аргументы вида `/Backups` в пути Windows. Используйте `MSYS_NO_PATHCONV=1` или запускайте из PowerShell/cmd.
