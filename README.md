# Belka

Утилита для выгрузки бэкапов в облачные хранилища и автоматического зеркалирования релизов GitHub и файлов по ссылкам. Один самодостаточный бинарник (Windows / Linux, в том числе ARM64), рассчитанный на запуск из планировщика.

---

## ✨ Возможности

**Провайдеры**

| Ключ `-p` | Хранилище | Проверка «файл не изменился» |
|---|---|---|
| `yandex` | Яндекс.Диск (REST API) | размер + MD5 |
| `mailru` | Облако Mail.ru (WebDAV) | размер + дата изменения |
| `google` | Google Drive (API v3, resumable upload) | размер + MD5 |
| `webdav` | Nextcloud, ownCloud, Koofr, pCloud, 4shared, InfiniCLOUD, Synology и любой WebDAV | размер + дата (MD5 при `WEBDAV_ETAG_IS_MD5=true`) |
| `s3` | AWS S3, Cloudflare R2, Backblaze B2, Wasabi, Yandex Object Storage, Selectel, VK Cloud, Timeweb, Storj, DigitalOcean Spaces, MinIO | размер + MD5 (для multipart — дата) |
| `synology` | Synology NAS (File Station API) | размер + дата изменения |

Адреса и настройки популярных S3- и WebDAV-сервисов собраны в разделе [Пресеты S3 и WebDAV](#пресеты-s3-и-webdav). В GUI их можно выбрать из списка.

**Режим 1 — выгрузка файла или папки.** Дерево каталогов воссоздаётся в облаке, неизменённые файлы пропускаются. Если у провайдера нет MD5, сравнивается дата изменения: это важно для многотомных архивов, где все тома одного размера. Загрузки идут параллельно (`-j`).

**Режим 2 — зеркалирование ссылок** (если путь не указан). Список берётся из `urls.txt`:
1. `--urls-file <PATH>`: локальный файл или путь в облаке;
2. `./urls.txt`, затем `urls.txt` рядом с бинарником;
3. `{remote_dir}/urls.txt` в облаке, затем `/urls.txt`.

Поддерживаемые виды ссылок:
* `https://github.com/owner/repo` — последний релиз; `.../releases/tag/<tag>` — конкретный релиз. Ассеты, подходящие под `--assets`, сохраняются в `{remote}/{repo}/[tag] имя_файла`. Старые версии того же файла удаляются **только после** успешной загрузки новой. Чужие файлы не трогаются.
* Любые прямые ссылки: файл скачивается и заливается, если его MD5 отличается от облачного.

**Режим 3 — восстановление** (`--restore`). Папка или файл из облака скачиваются на диск. Неизменённые файлы пропускаются, прерванное восстановление продолжается с места остановки. Подробнее см. [Восстановление](#восстановление-из-облака).

**Ротация бэкапов** (`--keep-last`, `--keep-days`). После успешной выгрузки старые бэкапы удаляются, в облаке остаются последние N штук или бэкапы за последние N дней. Бэкап распознаётся по дате в имени, тома многотомного архива удаляются вместе. Подробнее см. [Ротация](#ротация-старых-бэкапов).

**Уведомления.** Итог запуска уходит в Telegram, webhook (Slack, Discord, Mattermost) и сервис мониторинга вроде healthchecks.io: если бэкап сломался или перестал запускаться, вы узнаете об этом сразу. Подробнее см. [Уведомления](#уведомления).

**Шифрование** (любой провайдер, формат [rclone crypt](https://rclone.org/crypt/)). Файлы шифруются на вашем компьютере до отправки и расшифровываются после скачивания, облако видит только шифротекст. Имена файлов и папок тоже можно шифровать. Зашифрованное Belka открывается в rclone, и наоборот. Подробнее см. [Шифрование](#шифрование).

**Надёжность**
* Повторы с экспоненциальной задержкой при сетевых сбоях, 5xx и 429 (с учётом `Retry-After`), в том числе для самих загрузок.
* Без общего тайм-аута на передачу: многогигабайтные файлы не обрываются. Зависшие соединения отсекаются keep-alive и тайм-аутом, пропорциональным размеру.
* Ограниченное потребление памяти: файлы передаются потоком. S3 загружает файлы больше 64 МБ частями (multipart), Google Drive продолжает прерванную загрузку с места обрыва.
* Скачивание (зеркалирование ссылок, а в GUI — файлы из облака) пишет во временный `.part` и докачивает с места обрыва через `Range`. Существующий файл заменяется только полностью скачанным.
* Перед `--clean` проверяются локальный путь и список ссылок, а облачный `urls.txt` не удаляется. Очистка корня `/` запрещена.
* `--dry-run` показывает, что будет загружено или удалено, ничего не меняя.
* Коды возврата для скриптов: `0` успех, `1` фатальная ошибка, `2` неверные аргументы, `3` часть файлов не удалась, `130` прервано Ctrl+C.

## 🚀 Сборка

Требуется Rust 1.80+. Команды `cargo` без `-p` собирают только CLI.

```cmd
build.bat          # всё: CLI для Windows, GUI и CLI для Linux ARM64
build.bat exe      # только CLI для Windows
build.bat gui      # только GUI: dist\belka-gui.exe и установщик
build.bat arm64    # только Linux ARM64 (через zig)
```
Готовые файлы складываются в `dist/`.

Ручная сборка:
```bash
cargo build --release                                          # текущая платформа
cargo build --release --target x86_64-unknown-linux-musl       # Linux x86_64
cargo zigbuild --release --target aarch64-unknown-linux-musl   # Linux ARM64
cargo test --workspace                                         # тесты
```

GUI (нужен Node.js 20+):
```bash
cd gui
npm install
npm run tauri dev      # запуск в режиме разработки
npm run tauri build    # установщик в target/release/bundle/
```
Аккаунты GUI хранятся в `accounts.json` в папке настроек приложения, а пароли и токены — в системном хранилище учётных данных (Windows Credential Manager, Keychain, Secret Service).

#### Вход через браузер (Google Drive, Яндекс.Диск)

Обычно достаточно нажать «Войти через браузер»: используется OAuth-приложение, встроенное в сборку. Своё приложение нужно, если в сборке его нет или вы хотите собственную квоту API. Для этого в диалоге «Новый аккаунт» отметьте «Своё OAuth-приложение». Введённые данные запоминаются.

* **Google**: в Google Cloud Console включите Google Drive API, настройте OAuth consent screen (в режиме Testing добавьте свой адрес в тестовые пользователи) и создайте OAuth client ID типа **Desktop app**. Нужны Client ID и Client secret: для настольных приложений secret не считается секретом.
* **Яндекс**: на [oauth.yandex.ru](https://oauth.yandex.ru/) создайте приложение с платформой «Веб-сервисы», Redirect URI `http://127.0.0.1:53682/` и доступами Яндекс.Диска: чтение, запись, информация о Диске. Достаточно Client ID: вход идёт по PKCE.

Встроенное приложение задаётся при сборке GUI и CLI:
```cmd
set BELKA_GOOGLE_CLIENT_ID=...apps.googleusercontent.com
set BELKA_GOOGLE_CLIENT_SECRET=...
set BELKA_YANDEX_CLIENT_ID=...
npm run tauri build
```
Токен Яндекса действует год, после этого нужно войти заново.

#### Предпросмотр

Пробел, двойной щелчок или «Просмотр» в контекстном меню показывают файл из облака без сохранения: картинки, видео, аудио, PDF и текст (UTF-8 и Windows-1251, первый мегабайт). Стрелки ← → листают файлы папки. Файл скачивается во временный кэш приложения, который очищается при запуске; файлы больше 100 МБ скачиваются только после подтверждения. В зашифрованных папках файлы расшифровываются на лету.

#### Ссылки на файлы

В контекстном меню облака есть «Поделиться ссылкой» и «Закрыть доступ по ссылке» (Яндекс.Диск, Google Drive, Облако Mail.ru). Объект становится доступен на чтение всем, у кого есть ссылка, а сама ссылка копируется в буфер обмена. В Google закрывается только доступ по ссылке: доступ, выданный конкретным людям, остаётся.

Для ссылок в Mail.ru нужен пароль приложения с полным доступом, подробнее см. [Облако Mail.ru](#облако-mailru).

## ⚙️ Настройка

Скопируйте [.env.example](.env.example) в `.env` в текущую папку или рядом с программой либо укажите `--env-file`. Системные переменные окружения имеют приоритет над `.env`. Значения `CLOUD_PROVIDER`, `CLOUD_REMOTE_DIR`, `CLOUD_JOBS` из `.env` работают как значения по умолчанию для ключей командной строки.

`belka --list-providers` выводит переменные, нужные каждому провайдеру.

**Google Drive и Яндекс.Диск.** Токен проще всего получить командой `belka --login google` (или `yandex`): откроется браузер, а после входа программа выведет строки для `.env`. Сообщения идут в stderr, поэтому можно сразу дописать файл: `belka --login google >> .env`. Вход нужен на компьютере с браузером, полученные строки можно перенести на сервер.

Для Google выводится `GOOGLE_REFRESH_TOKEN`, по нему access token обновляется автоматически. Refresh token работает только с тем OAuth-приложением, для которого выдан. Со встроенным приложением хватает одного токена. Если заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, вход и работа идут через ваше приложение (тип Desktop, scope `https://www.googleapis.com/auth/drive`). Вместо refresh token можно указать `GOOGLE_DRIVE_TOKEN`, но access token живёт около часа.

#### Облако Mail.ru

Обычный пароль от почты не подойдёт: нужен пароль для внешних приложений («Пароль и безопасность → Пароли для внешних приложений»). При создании выбирается уровень доступа:

| Уровень доступа | Файлы (WebDAV) | Ссылки в GUI |
|---|---|---|
| Полный доступ к Облаку (WebDAV) | ✅ | ❌ «username or password is incorrect» |
| Полный доступ к Почте, Облаку и Календарю (все протоколы) | ✅ | ✅ |

Ссылки создаются через API самого облака, а не через WebDAV, и с паролем только для WebDAV Mail.ru в этот API не пускает. Пароль в уже добавленном аккаунте поменять нельзя: удалите аккаунт и добавьте его заново.

**S3.** Используются path-style запросы (`{endpoint}/{bucket}/{key}`). В S3 нет настоящих папок, поэтому пустые каталоги не создаются. Регион подписи (`S3_REGION`) для известных сервисов определяется по адресу endpoint, для остальных по умолчанию берётся `us-east-1`. Если сервер отвечает ошибкой подписи, укажите регион явно.

#### Пресеты S3 и WebDAV

Многие хранилища работают по протоколу S3 или WebDAV, поэтому подключаются через провайдеры `s3` и `webdav`, отдельный код для них не нужен. В GUI при добавлении аккаунта S3 или WebDAV есть список «Сервис»: выбранный сервис подставляет известный адрес (или пример адреса, если он у каждого свой) и показывает, где взять ключи. В CLI те же значения указываются в `.env`.

**S3** (`-p s3`). Регион в колонке «Регион» определяется автоматически, задавать `S3_REGION` не нужно.

| Сервис | `S3_ENDPOINT` | Регион | Где взять ключи |
|---|---|---|---|
| Amazon S3 | `https://s3.<регион>.amazonaws.com` | из адреса | IAM → Users → Security credentials |
| Cloudflare R2 | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` | `auto` | R2 → Manage API tokens |
| Backblaze B2 | `https://s3.<регион>.backblazeb2.com` (указан на странице бакета) | из адреса | Application Keys: keyID и applicationKey |
| Wasabi | `https://s3.<регион>.wasabisys.com` | из адреса | Access Keys |
| Yandex Object Storage | `https://storage.yandexcloud.net` | `ru-central1` | статический ключ сервисного аккаунта с ролью `storage.editor` |
| Selectel | `https://s3.ru-1.storage.selcloud.ru` (для другого пула замените `ru-1`) | из адреса | S3-ключи сервисного пользователя |
| VK Cloud | `https://hb.ru-msk.vkcloud-storage.ru` | `ru-msk` | Объектное хранилище → Аккаунты |
| Timeweb Cloud | `https://s3.twcstorage.ru` | по умолчанию | вкладка «Дашборд» бакета |
| Storj | `https://gateway.storjshare.io` | по умолчанию | Access → Create S3 Credentials |
| DigitalOcean Spaces | `https://<регион>.digitaloceanspaces.com` | из адреса | API → Spaces Keys |
| MinIO | `http://<сервер>:9000` | по умолчанию | Access Keys в консоли MinIO |

Например, для Backblaze B2 достаточно четырёх строк:
```ini
S3_ENDPOINT=https://s3.eu-central-003.backblazeb2.com
S3_BUCKET=my-backups
S3_ACCESS_KEY_ID=003a1b2c...
S3_SECRET_ACCESS_KEY=K003...
```

**WebDAV** (`-p webdav`).

| Сервис | `WEBDAV_URL` | Пользователь и пароль |
|---|---|---|
| Nextcloud | `https://<сервер>/remote.php/dav/files/<пользователь>/` | пароль приложения: Настройки → Безопасность |
| ownCloud | `https://<сервер>/remote.php/webdav/` | логин и пароль (или пароль приложения) |
| Koofr | `https://app.koofr.net/dav/Koofr` | e-mail и пароль приложения: Preferences → Passwords |
| pCloud | `https://ewebdav.pcloud.com` (аккаунты в ЕС) или `https://webdav.pcloud.com` (США) | e-mail и пароль |
| 4shared | `https://webdav.4shared.com` | e-mail и пароль |
| InfiniCLOUD | `https://<сервер>.teracloud.jp/dav/` | пароль приложения: My Page → Apps Connection |
| Synology (пакет WebDAV Server) | `https://<NAS>:5006` | пользователь DSM; без пакета используйте `-p synology` |

**Synology.** Работает через API File Station, как веб-интерфейс DSM: пакет WebDAV Server не нужен. Адрес — IP или имя NAS (`192.168.1.10`) либо полный URL (`https://nas.example.com:5001`). Порт — тот, что в адресе DSM в браузере (Панель управления → Портал входа): по умолчанию 5000, а с `SYNOLOGY_HTTPS=true` — 5001, другой задаётся в `SYNOLOGY_PORT`. Для самоподписанного сертификата включите `SYNOLOGY_INSECURE=true`. Двухфакторная аутентификация не поддерживается: заведите для Belka отдельного пользователя DSM без неё. Верхний уровень — общие папки (`/home`, `/photo`, …); их создают и удаляют в DSM. В GUI ссылки создаются как кнопкой «Поделиться» в File Station, можно задать пароль и срок действия. Адрес в ссылке DSM берёт из своих настроек (Панель управления → Внешний доступ).

#### Шифрование

Формат полностью совпадает с rclone crypt: содержимое шифруется XSalsa20-Poly1305 блоками по 64 КБ, имена — AES-256 в режиме EME, ключи получаются из пароля через scrypt. Belka и rclone читают файлы друг друга.

**Пароль не восстанавливается.** Без него файлы не расшифровать ни Belka, ни rclone, ни кому-либо ещё.

**В GUI.** «Новый аккаунт → Зашифрованная папка»: выберите подключённое облако, папку в нём (например `/Encrypted`) и пароль. Папка появится отдельным аккаунтом: всё, что загружается в неё, шифруется, а при просмотре и скачивании расшифровывается. Пароль хранится в системном хранилище учётных данных. Если в папке уже есть файлы, Belka проверит, что они расшифровываются этим паролем. Облако, в котором лежат зашифрованные папки, нельзя удалить, пока не удалены они. В обычном облаке зашифрованная папка и её содержимое помечены замком, а двойной щелчок по такой папке открывает её расшифрованный вид.

**В CLI** шифрование включается переменной `CRYPT_PASSWORD`:

| Переменная | Что задаёт |
|---|---|
| `CRYPT_PASSWORD` | пароль; если задан, все файлы шифруются |
| `CRYPT_PASSWORD2` | необязательная соль, `password2` в rclone |
| `CRYPT_ROOT` | папка облака с зашифрованным деревом, по умолчанию `/` |
| `CRYPT_FILENAMES` | `standard` (по умолчанию, имена шифруются) или `off` |

Путь `-r` отсчитывается внутри `CRYPT_ROOT`: с `CRYPT_ROOT=/Encrypted` и `-r /Backups` файлы лягут в `/Encrypted/<шифрованное «Backups»>/…`. Чтобы видеть эти бэкапы в GUI, создайте зашифрованную папку `/Encrypted` с тем же паролем.

**Как открыть в rclone:** remote типа `crypt` с `remote = <облако>:<папка>`, тем же паролем и `filename_encryption = standard` (или `off`). В `rclone.conf` пароли хранятся в скрытом виде, а Belka нужен исходный пароль: его показывает `rclone reveal`.

Шифрование идёт на лету, без временных файлов: данные шифруются блоками по 64 КБ во время отправки и расшифровываются во время скачивания. Возобновление прерванной загрузки (Google Drive) и докачка работают и для зашифрованных файлов.

Ограничения:
* MD5 у зашифрованных файлов не совпадает с исходным, поэтому неизменённые файлы определяются по размеру и дате. При зеркалировании прямые ссылки без тега версии загружаются заново при каждом запуске.
* Зашифрованное имя длиннее исходного. У облаков с лимитом 255 символов на имя исходное имя должно быть не длиннее примерно 140 байт (около 70 кириллических символов).
* Ссылками на зашифрованные файлы делиться нельзя: получатель увидит только шифротекст.

## 📖 Использование

```text
belka [OPTIONS] [LOCAL_PATH]

  -p, --provider <PROVIDER>  yandex | mailru | google | webdav | s3 | synology   [env: CLOUD_PROVIDER] [default: yandex]
  -r, --remote <REMOTE>      Папка в облаке; {date}, {time}, {datetime} заменяются текущими
                             датой и временем                         [env: CLOUD_REMOTE_DIR] [default: /Upload]
      --restore              Скачать папку (или файл) --remote в LOCAL_PATH
      --keep-last <N>        После выгрузки оставить N последних бэкапов каждой серии
      --keep-days <N>        После выгрузки оставить бэкапы за последние N дней (включая сегодня)
      --notify-on <WHEN>     failure | always: когда писать в Telegram и webhook  [env: NOTIFY_ON] [default: failure]
      --notify-test          Отправить тестовое уведомление и выйти
      --env-file <FILE>      Путь к .env
      --urls-file <PATH>     Список ссылок: локальный файл или путь в облаке  [env: CLOUD_URLS_FILE]
  -c, --clean                Очистить папку в облаке перед загрузкой
  -f, --overwrite            Загружать (при --restore — скачивать) даже неизменённые файлы
  -n, --dry-run              Только показать, что будет сделано
  -j, --jobs <JOBS>          Параллельные загрузки и скачивания, 1..32  [env: CLOUD_JOBS] [default: 2]
      --assets <REGEX>       Какие ассеты релизов скачивать            [default: (?i)\.(apk|exe|zip|tar\.gz)$]
      --list-providers       Список провайдеров и их переменных
      --login <PROVIDER>     Войти в google или yandex через браузер и вывести строки для .env
  -v, --verbose / -q, --quiet
```

### Дата в пути

В `-r` можно подставить текущую локальную дату и время:

| Шаблон | Пример |
|---|---|
| `{date}` | `2026-10-15` |
| `{time}` | `03-00-00` |
| `{datetime}` | `2026-10-15_03-00-00` |

`belka -r "/Backups/{date}" D:\Data` каждый день кладёт копию в новую папку: `/Backups/2026-10-15`, `/Backups/2026-10-16` и так далее. Учтите, что в новую папку каждый раз загружается всё целиком: пропуск неизменённых файлов работает только внутри одной папки. Другие шаблоны в фигурных скобках считаются ошибкой.

### Примеры

```powershell
# Папка бэкапа на Яндекс.Диск
belka.exe -p yandex -r /Backups/2026.09.17 D:\Backups\Daily

# Сначала посмотреть, что изменится
belka.exe -p mailru -r /Backups/Latest -c -n D:\Backups\Daily

# Cloudflare R2, 4 параллельные загрузки
belka.exe -p s3 -r /daily-snapshots -j 4 C:\Data

# Зеркалирование релизов, только .apk
belka.exe -p google -r /Mirror --assets "(?i)\.apk$"

# Ежедневная копия в папку с датой, хранить 14 последних
belka.exe -p yandex -r "/Backups/{date}" --keep-last 14 D:\Data

# Восстановить копию за 15 октября
belka.exe -p yandex --restore -r /Backups/2026-10-15 D:\Restore

# Проверить настройки уведомлений
belka.exe --notify-test
```

### Ротация старых бэкапов

Ротация удаляет из облака старые бэкапы, чтобы они не копились бесконечно. Она включается ключами `--keep-last N` и/или `--keep-days N` и работает только при выгрузке (режим 1), сразу после неё.

**Как Belka находит бэкапы.** Бэкапом считается файл или папка, в имени которых есть дата. Поддерживаемые форматы:

| Пример имени | Распознанная дата |
|---|---|
| `db_2026-10-15.sql.gz` | 15.10.2026 |
| `2026_10_15`, `2026.10.15`, `20261015` | 15.10.2026 |
| `site-20261015_0300.7z` | 15.10.2026 03:00 |
| `site 2026-10-15 03-00-15.zip`, `x_2026-10-15T030015.tar` | 15.10.2026 03:00:15 |

Год должен быть от 1990 до 2200, а дата существующей. Файлы и папки **без даты в имени ротация никогда не трогает**: `urls.txt`, `readme.txt`, `backup.zip` останутся на месте.

**Серии.** Имена, которые отличаются только датой, образуют серию: `db_2026-10-14.sql.gz` и `db_2026-10-15.sql.gz` относятся к серии `db_*.sql.gz`, а `site_2026-10-15.7z` — к серии `site_*.7z`. Правила применяются к каждой серии отдельно, поэтому в одной папке можно хранить бэкапы разных систем: `--keep-last 7` оставит 7 последних бэкапов базы **и** 7 последних бэкапов сайта.

**Многотомные архивы.** Тома одного архива (`.7z.001`, `.7z.002`, …, `.part01.rar`, `.z01`, `.r00`) считаются одним бэкапом и удаляются вместе.

**Правила.**
* `--keep-last N`: в каждой серии остаются N самых новых бэкапов (по дате из имени).
* `--keep-days N`: остаются бэкапы, датированные последними N днями, включая сегодня. `--keep-days 7` от 15 октября сохранит бэкапы с 9 по 15 октября.
* Если заданы оба ключа, бэкап остаётся, когда его сохраняет **хотя бы одно** правило. `--keep-last 3 --keep-days 30` хранит всё за месяц, но не меньше трёх бэкапов, даже если бэкапы давно не делались.

**В какой папке.** Обычно ротация работает в папке `-r`. Если в `-r` есть шаблон даты, ротация идёт в родительской папке первого сегмента с шаблоном: при `-r "/Backups/{date}"` это `/Backups`, и бэкапами там будут папки `2026-10-14`, `2026-10-15`, … Учитываются только элементы, лежащие прямо в этой папке, вложенные не просматриваются.

**Защита от потери данных.**
* Если при выгрузке хоть один файл не загрузился, ротация не выполняется, и старые бэкапы остаются: неудачная новая копия не должна стоить удачной старой. В лог пишется `Rotation skipped`.
* Не удаляется то, что записал текущий запуск: загруженный файл, папка с датой из шаблона, а при выгрузке папки — всё, что лежит в ней на верхнем уровне.
* С `--dry-run` ротация только показывает, что удалила бы.
* Если удаление не удалось, код возврата будет `3`.

> ⚠️ Не включайте ротацию для папки-зеркала, в которой лежат ваши собственные файлы с датами в именах (например фото `IMG_20261015_…`). Такие файлы будут приняты за бэкапы. Ротацию стоит включать для папки, отведённой только под бэкапы.

**Типичные схемы.**

Архив с датой в имени: скрипт создаёт архив, Belka выгружает его и удаляет лишние.
```powershell
$name = "db_$(Get-Date -Format yyyy-MM-dd).7z"
7z a "D:\Out\$name" D:\Database
belka.exe -p s3 -r /Backups --keep-last 7 "D:\Out\$name"
```
```bash
name="db_$(date +%F).tar.gz"
tar czf "/tmp/$name" /var/lib/app && ./belka -q -r /Backups --keep-days 30 "/tmp/$name"
```

Копия папки целиком, по папке на каждый день:
```powershell
belka.exe -p yandex -r "/Backups/{date}" --keep-last 7 D:\Data
```

### Восстановление из облака

`--restore` работает в обратную сторону: содержимое папки `-r` скачивается в локальную папку `LOCAL_PATH`.

```powershell
# Вся папка: /Backups/2026-10-15/… → D:\Restore\…
belka.exe -p yandex --restore -r /Backups/2026-10-15 D:\Restore

# Один файл: сохранится как D:\Restore\db_2026-10-15.7z
belka.exe -p s3 --restore -r /Backups/db_2026-10-15.7z D:\Restore

# Посмотреть, что будет скачано
belka.exe -p yandex --restore -r /Backups/2026-10-15 -n D:\Restore
```

Как это работает:
* `LOCAL_PATH` — всегда папка; если её нет, она создаётся. Если `-r` указывает на папку, её содержимое со всеми подпапками попадает прямо в `LOCAL_PATH`, а если на файл — файл сохраняется в `LOCAL_PATH` под своим именем.
* Уже существующие файлы с тем же размером и тем же MD5 (если облако его отдаёт) или той же датой изменения пропускаются. Поэтому прерванное восстановление можно просто запустить заново. `-f` скачивает всё заново.
* Каждый файл пишется во временный `.part` и докачивается после обрыва связи. Существующий файл заменяется только полностью скачанным.
* Скачанным файлам ставится дата изменения из облака. Так последующая выгрузка этих же файлов обратно увидит их неизменёнными.
* Файлы, которых нет в облаке, в локальной папке не удаляются.
* Имена, недопустимые в Windows (`:`, `*`, `?` и т. п.), а также `..` заменяются безопасными (`_`), и в лог пишется предупреждение.
* Параллельность задаётся `-j`, как и при выгрузке.
* **Шифрование.** С `CRYPT_PASSWORD` файлы расшифровываются при скачивании, а `-r` указывается в незашифрованном виде внутри `CRYPT_ROOT`, как и при выгрузке.
* `--restore` нельзя сочетать с `--clean`, `--keep-last` и `--keep-days`.

### Уведомления

Belka сообщает об итоге запуска в один или несколько каналов. Каналы включаются переменными в `.env` или окружении:

| Канал | Переменные | Что приходит |
|---|---|---|
| Telegram | `NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT` | текстовое сообщение |
| Webhook | `NOTIFY_WEBHOOK_URL` | POST с JSON |
| Пинг мониторинга | `NOTIFY_PING_URL` | запросы в стиле [healthchecks.io](https://healthchecks.io) |

Дополнительно:
* `NOTIFY_ON` (или `--notify-on`): `failure` (по умолчанию) пишет в Telegram и webhook только о проблемах, `always` — о каждом запуске.
* `NOTIFY_NAME`: название задания в сообщениях, например `nightly-db`. Полезно, если заданий несколько.
* `NOTIFY_TELEGRAM_API`: адрес Bot API, по умолчанию `https://api.telegram.org`. Пригодится, если доступ к Telegram заблокирован: можно указать свой [сервер Bot API](https://github.com/tdlib/telegram-bot-api) или обратный прокси.

**Статусы.** Сообщение отправляется в конце каждого запуска с одним из статусов:

| Статус | Когда | Код возврата |
|---|---|---|
| ✅ `success` | всё загружено (или скачано) | `0` |
| ⚠️ `partial` | часть файлов или удалений не удалась | `3` |
| ❌ `failure` | фатальная ошибка: нет доступа, неверные настройки, ошибка в шаблоне пути | `1` |
| ⏹ `interrupted` | прервано Ctrl+C | `130` |

Пример сообщения:
```text
⚠️ Backup finished with errors — nightly-db
Host: SERVER01
Target: yandex /Backups/2026-10-15 (upload)
Files: 12 uploaded (1.2 GB), 30 unchanged, 1 failed
Deleted: 2
Time: 5m 12s
```

**Проверка.** `belka --notify-test` отправляет тестовое сообщение во все настроенные каналы и сообщает, какой сработал, а какой нет.

Важно знать:
* При `--dry-run` уведомления не отправляются, чтобы пробный запуск не выглядел для мониторинга как настоящий бэкап.
* Ошибка отправки уведомления пишется в лог как предупреждение и не меняет код возврата.
* Об ошибках в аргументах командной строки (код `2`) уведомлений нет: до запуска дело не доходит.
* Токен бота не попадает в лог даже при ошибках сети.

#### Telegram

1. Напишите [@BotFather](https://t.me/BotFather) команду `/newbot` и получите токен вида `123456789:AAH…`. Это `NOTIFY_TELEGRAM_TOKEN`.
2. Узнайте ID чата (`NOTIFY_TELEGRAM_CHAT`):
   * **личные сообщения:** напишите боту что угодно и откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, ID — поле `chat.id`;
   * **группа:** добавьте бота в группу, напишите в ней сообщение и посмотрите `getUpdates`, ID группы отрицательный;
   * **канал:** добавьте бота администратором канала с правом публикации; ID канала имеет вид `-100…`, можно указать и `@имя_канала` для публичного канала.
3. Проверьте: `belka --notify-test`.

#### Webhook

На `NOTIFY_WEBHOOK_URL` отправляется POST с JSON:
```json
{
  "status": "partial",
  "name": "nightly-db",
  "host": "SERVER01",
  "mode": "upload",
  "provider": "yandex",
  "remote": "/Backups/2026-10-15",
  "processed": 43, "uploaded": 12, "skipped": 30, "deleted": 2, "failed": 1,
  "bytes": 1288490188,
  "duration_secs": 312,
  "error": null,
  "version": "1.1.0",
  "text": "⚠️ Backup finished with errors — nightly-db\n…",
  "content": "⚠️ Backup finished with errors — nightly-db\n…"
}
```
`mode` принимает значения `upload`, `restore` или `mirror`, `bytes` — объём загруженного (при восстановлении — скачанного), `error` — текст фатальной ошибки. Готовый текст сообщения лежит сразу в двух полях: `text` читают входящие webhook Slack, Mattermost и Rocket.Chat, а `content` — Discord. Поэтому адрес их webhook можно указать как есть. Для своих систем (n8n, Home Assistant, скрипт) используйте остальные поля.

#### Мониторинг (healthchecks.io)

Уведомление приходит, когда запуск закончился ошибкой. Но если бэкап перестал запускаться совсем (выключен сервер, сломан планировщик), сообщать будет некому. Эту проблему решает «dead man's switch»: сервис мониторинга ждёт сигнал по расписанию и бьёт тревогу, если сигнал не пришёл.

1. Создайте check на [healthchecks.io](https://healthchecks.io) (или на своём сервере Healthchecks), задайте период и допустимую задержку под ваше расписание.
2. Укажите его адрес: `NOTIFY_PING_URL=https://hc-ping.com/<uuid>`.

Belka отправляет POST на `<URL>/start` в начале запуска (сервис измеряет длительность и замечает зависшие запуски), на `<URL>` при успехе и на `<URL>/fail` при любой проблеме. В теле запроса — текст отчёта, он виден в журнале событий check'а. Пинг отправляется после каждого запуска, независимо от `NOTIFY_ON`.

### Запуск по расписанию (cron)

```bash
0 3 * * * cd /opt/belka && ./belka -q /srv/backups >> /var/log/belka.log 2>&1 || echo "backup failed: $?"
```
Ненулевой код возврата означает проблему: `3` — часть файлов не загрузилась (подробности в логе). Чтобы узнавать о проблемах без чтения логов, настройте [уведомления](#уведомления). Защитите `.env` правами `chmod 600 .env`. Секреты никогда не передаются через аргументы командной строки и не видны в списке процессов.

> **Git Bash на Windows** превращает аргументы вида `/Backups` в пути Windows. Используйте `MSYS_NO_PATHCONV=1` или запускайте из PowerShell/cmd.
