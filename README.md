# Belka

Утилита для выгрузки бэкапов в облачные хранилища и автоматического зеркалирования релизов GitHub и файлов по ссылкам. Один самодостаточный бинарник (Windows / Linux, в том числе ARM64), рассчитанный на запуск из планировщика.

---

## ✨ Возможности

**Провайдеры**

| Ключ `-p` | Хранилище | Проверка «файл не изменился» |
|---|---|---|
| `yandex` | Яндекс.Диск (REST API) | размер + MD5 |
| `mailru` | Облако Mail.ru (WebDAV) | размер + дата изменения |
| `google` | Google Drive (API v3, resumable upload) | размер + MD5 |
| `webdav` | Nextcloud, ownCloud, Synology и любой WebDAV | размер + дата (MD5 при `WEBDAV_ETAG_IS_MD5=true`) |
| `s3` | AWS S3, Cloudflare R2, MinIO, Yandex Object Storage | размер + MD5 (для multipart — дата) |

**Режим 1 — выгрузка файла или папки.** Дерево каталогов воссоздаётся в облаке, неизменённые файлы пропускаются. Если у провайдера нет MD5, сравнивается дата изменения: это важно для многотомных архивов, где все тома одного размера. Загрузки идут параллельно (`-j`).

**Режим 2 — зеркалирование ссылок** (если путь не указан). Список берётся из `urls.txt`:
1. `--urls-file <PATH>`: локальный файл или путь в облаке;
2. `./urls.txt`, затем `urls.txt` рядом с бинарником;
3. `{remote_dir}/urls.txt` в облаке, затем `/urls.txt`.

Поддерживаемые виды ссылок:
* `https://github.com/owner/repo` — последний релиз; `.../releases/tag/<tag>` — конкретный релиз. Ассеты, подходящие под `--assets`, сохраняются в `{remote}/{repo}/[tag] имя_файла`. Старые версии того же файла удаляются **только после** успешной загрузки новой. Чужие файлы не трогаются.
* Любые прямые ссылки: файл скачивается и заливается, если его MD5 отличается от облачного.

**Надёжность**
* Повторы с экспоненциальной задержкой при сетевых сбоях, 5xx и 429 (с учётом `Retry-After`), в том числе для самих загрузок.
* Без общего тайм-аута на передачу: многогигабайтные файлы не обрываются. Зависшие соединения отсекаются keep-alive и тайм-аутом, пропорциональным размеру.
* Ограниченное потребление памяти: файлы передаются потоком. S3 загружает файлы больше 64 МБ частями (multipart), Google Drive продолжает прерванную загрузку с места обрыва.
* Скачивание (зеркалирование ссылок, а в GUI — файлы из облака) пишет во временный `.part` и докачивает с места обрыва через `Range`. Существующий файл заменяется только полностью скачанным.
* Перед `--clean` проверяются локальный путь и список ссылок, а облачный `urls.txt` не удаляется. Очистка корня `/` запрещена.
* `--dry-run` показывает, что будет загружено или удалено, ничего не меняя.
* Коды возврата для скриптов: `0` успех, `1` фатальная ошибка, `2` неверные аргументы, `3` часть файлов не удалась, `130` прервано Ctrl+C.

## 🗂 Структура

Репозиторий — Cargo workspace:

| Каталог | Что внутри |
|---|---|
| `crates/core` | Провайдеры облаков, HTTP-ретраи, утилиты. Общая библиотека для CLI и GUI |
| `crates/cli` | Консольная утилита `belka` для скриптов и планировщика |
| `gui/` | Настольное приложение на Tauri 2 + Svelte (в разработке) |

## 🚀 Сборка

Требуется Rust 1.80+. Команды `cargo` без `-p` собирают только CLI.

```cmd
build.bat          # всё: CLI для Windows, GUI и CLI для Linux ARM64
build.bat exe      # только CLI для Windows
build.bat gui      # только GUI: dist\belka-gui.exe и установщик
build.bat arm64    # только Linux ARM64 (через zig)
```
Готовые файлы складываются в `dist/`.

Ручная сборка:
```bash
cargo build --release                                          # текущая платформа
cargo build --release --target x86_64-unknown-linux-musl       # Linux x86_64
cargo zigbuild --release --target aarch64-unknown-linux-musl   # Linux ARM64
cargo test --workspace                                         # тесты
```

GUI (нужен Node.js 20+):
```bash
cd gui
npm install
npm run tauri dev      # запуск в режиме разработки
npm run tauri build    # установщик в target/release/bundle/
```
Аккаунты GUI хранятся в `accounts.json` в папке настроек приложения, а пароли и токены — в системном хранилище учётных данных (Windows Credential Manager, Keychain, Secret Service).

#### Вход через браузер (Google Drive, Яндекс.Диск)

Обычно достаточно нажать «Войти через браузер»: используется OAuth-приложение, встроенное в сборку. Своё приложение нужно, если в сборке его нет или вы хотите собственную квоту API. Для этого в диалоге «Новый аккаунт» отметьте «Своё OAuth-приложение». Введённые данные запоминаются.

* **Google**: в Google Cloud Console включите Google Drive API, настройте OAuth consent screen (в режиме Testing добавьте свой адрес в тестовые пользователи) и создайте OAuth client ID типа **Desktop app**. Нужны Client ID и Client secret: для настольных приложений secret не считается секретом.
* **Яндекс**: на [oauth.yandex.ru](https://oauth.yandex.ru/) создайте приложение с платформой «Веб-сервисы», Redirect URI `http://127.0.0.1:53682/` и доступами Яндекс.Диска: чтение, запись, информация о Диске. Достаточно Client ID: вход идёт по PKCE.

Встроенное приложение задаётся при сборке GUI и CLI:
```cmd
set BELKA_GOOGLE_CLIENT_ID=...apps.googleusercontent.com
set BELKA_GOOGLE_CLIENT_SECRET=...
set BELKA_YANDEX_CLIENT_ID=...
npm run tauri build
```
Токен Яндекса действует год, после этого нужно войти заново.

#### Ссылки на файлы

В контекстном меню облака есть «Поделиться ссылкой» и «Закрыть доступ по ссылке» (Яндекс.Диск, Google Drive, Облако Mail.ru). Объект становится доступен на чтение всем, у кого есть ссылка, а сама ссылка копируется в буфер обмена. В Google закрывается только доступ по ссылке: доступ, выданный конкретным людям, остаётся.

Для ссылок в Mail.ru нужен пароль приложения с полным доступом, подробнее см. [Облако Mail.ru](#облако-mailru).

## ⚙️ Настройка

Скопируйте [.env.example](.env.example) в `.env` в текущую папку или рядом с программой либо укажите `--env-file`. Системные переменные окружения имеют приоритет над `.env`. Значения `CLOUD_PROVIDER`, `CLOUD_REMOTE_DIR`, `CLOUD_JOBS` из `.env` работают как значения по умолчанию для ключей командной строки.

`belka --list-providers` выводит переменные, нужные каждому провайдеру.

**Google Drive и Яндекс.Диск.** Токен проще всего получить командой `belka --login google` (или `yandex`): откроется браузер, а после входа программа выведет строки для `.env`. Сообщения идут в stderr, поэтому можно сразу дописать файл: `belka --login google >> .env`. Вход нужен на компьютере с браузером, полученные строки можно перенести на сервер.

Для Google выводится `GOOGLE_REFRESH_TOKEN`, по нему access token обновляется автоматически. Refresh token работает только с тем OAuth-приложением, для которого выдан. Со встроенным приложением хватает одного токена. Если заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, вход и работа идут через ваше приложение (тип Desktop, scope `https://www.googleapis.com/auth/drive`). Вместо refresh token можно указать `GOOGLE_DRIVE_TOKEN`, но access token живёт около часа.

#### Облако Mail.ru

Обычный пароль от почты не подойдёт: нужен пароль для внешних приложений («Пароль и безопасность → Пароли для внешних приложений»). При создании выбирается уровень доступа:

| Уровень доступа | Файлы (WebDAV) | Ссылки в GUI |
|---|---|---|
| Полный доступ к Облаку (WebDAV) | ✅ | ❌ «username or password is incorrect» |
| Полный доступ к Почте, Облаку и Календарю (все протоколы) | ✅ | ✅ |

Ссылки создаются через API самого облака, а не через WebDAV, и с паролем только для WebDAV Mail.ru в этот API не пускает. Пароль в уже добавленном аккаунте поменять нельзя: удалите аккаунт и добавьте его заново.

**S3.** Используются path-style запросы (`{endpoint}/{bucket}/{key}`). В S3 нет настоящих папок, поэтому пустые каталоги не создаются.

## 📖 Использование

```text
belka [OPTIONS] [LOCAL_PATH]

  -p, --provider <PROVIDER>  yandex | mailru | google | webdav | s3   [env: CLOUD_PROVIDER] [default: yandex]
  -r, --remote <REMOTE>      Папка в облаке                           [env: CLOUD_REMOTE_DIR] [default: /Upload]
      --env-file <FILE>      Путь к .env
      --urls-file <PATH>     Список ссылок: локальный файл или путь в облаке  [env: CLOUD_URLS_FILE]
  -c, --clean                Очистить папку в облаке перед загрузкой
  -f, --overwrite            Загружать даже неизменённые файлы
  -n, --dry-run              Только показать, что будет сделано
  -j, --jobs <JOBS>          Параллельные загрузки, 1..32              [env: CLOUD_JOBS] [default: 2]
      --assets <REGEX>       Какие ассеты релизов скачивать            [default: (?i)\.(apk|exe|zip|tar\.gz)$]
      --list-providers       Список провайдеров и их переменных
      --login <PROVIDER>     Войти в google или yandex через браузер и вывести строки для .env
  -v, --verbose / -q, --quiet
```

### Примеры

```powershell
# Папка бэкапа на Яндекс.Диск
belka.exe -p yandex -r /Backups/2026.09.17 D:\Backups\Daily

# Сначала посмотреть, что изменится
belka.exe -p mailru -r /Backups/Latest -c -n D:\Backups\Daily

# Cloudflare R2, 4 параллельные загрузки
belka.exe -p s3 -r /daily-snapshots -j 4 C:\Data

# Зеркалирование релизов, только .apk
belka.exe -p google -r /Mirror --assets "(?i)\.apk$"
```

### Запуск по расписанию (cron)

```bash
0 3 * * * cd /opt/belka && ./belka -q /srv/backups >> /var/log/belka.log 2>&1 || echo "backup failed: $?"
```
Ненулевой код возврата означает проблему: `3` — часть файлов не загрузилась (подробности в логе). Защитите `.env` правами `chmod 600 .env`. Секреты никогда не передаются через аргументы командной строки и не видны в списке процессов.

> **Git Bash на Windows** превращает аргументы вида `/Backups` в пути Windows. Используйте `MSYS_NO_PATHCONV=1` или запускайте из PowerShell/cmd.
